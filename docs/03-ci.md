# Continuous Integration

Run ReelOut in CI to automate releases when changes land on your main branch.
The examples below show the minimum setup; adapt permissions, secrets, and
package-manager steps to your project.

## GitHub Actions

Create `.github/workflows/release.yml`:

```yaml
name: Release

on:
  push:
    branches:
      - main
  workflow_dispatch:
    inputs:
      type:
        description: 'Choose a release type instead of deriving it from commits; use auto to analyze commits.'
        type: choice
        options:
          - auto
          - major
          - minor
          - patch
        default: auto
      qualifier:
        description: 'Set the SemVer prerelease identifier; use false to disable it or true to follow branch rules.'
        type: string
      channel:
        description: 'Set the release channel, applied as the npm dist-tag; use false to disable it or true to follow branch rules.'
        type: string
      allow-empty:
        description: 'Run the release workflow even when no releasable changes are detected.'
        type: boolean
        default: false
      dry-run:
        description: 'Preview the release without writing files, creating commits or tags, or publishing packages or releases.'
        type: boolean
        default: false

permissions:
  contents: write
  id-token: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - name: Release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
          RELEASE_TYPE: ${{ inputs.type }}
          RELEASE_QUALIFIER: ${{ inputs.qualifier }}
          RELEASE_CHANNEL: ${{ inputs.channel }}
          ALLOW_EMPTY: ${{ inputs['allow-empty'] }}
          DRY_RUN: ${{ inputs['dry-run'] }}
        run: |
          ARGS=()
          if [[ -n "$RELEASE_TYPE" ]]; then ARGS+=(--type "$RELEASE_TYPE"); fi
          if [[ -n "$RELEASE_QUALIFIER" ]]; then ARGS+=(--qualifier "$RELEASE_QUALIFIER"); fi
          if [[ -n "$RELEASE_CHANNEL" ]]; then ARGS+=(--channel "$RELEASE_CHANNEL"); fi
          if [[ "$ALLOW_EMPTY" == "true" ]]; then ARGS+=(--allow-empty); fi
          if [[ "$DRY_RUN" == "true" ]]; then ARGS+=(--dry-run); fi
          npx reelout "${ARGS[@]}"
```

### Notes

- **Permissions:** `contents: write` lets ReelOut push tags and create GitHub releases. `id-token: write` enables npm provenance and [npm trusted publishing](#npm-trusted-publishing); remove it when publishing with `NPM_TOKEN` and provenance is disabled. Add `packages: write` only if publishing to GitHub Packages.
- **Secrets:** Add `NPM_TOKEN` to repository secrets when publishing to npm, and `CARGO_REGISTRY_TOKEN` when publishing crates. With [npm trusted publishing](#npm-trusted-publishing) or [Cargo trusted publishing](#cargo-trusted-publishing), no registry token is needed. GitHub Actions provides `GITHUB_TOKEN`.
- **Missing credentials:** Steps without credentials are skipped with warnings and the job still succeeds. Add `--strict` when the pipeline must publish everything.
- **Using npm:** Replace the pnpm setup steps with `npm ci` and remove `cache: 'pnpm'`.

### Release report

When a release runs on GitHub Actions, ReelOut appends a Markdown release
report to the run's job summary. The report shows the release status, the
released versions and tags, and the changelogs, rendered next to the other
summary sections on the run page. Dry runs are marked with a `(dry run)`
suffix on the status line; real releases show the status unmarked. A failed
release also emits a GitHub Actions error annotation with the failure reason.
No configuration is required.

## npm trusted publishing

Publish to the public npm registry without storing an `NPM_TOKEN`. With
npm's trusted publishing, the CI platform issues an OIDC identity token that
npm exchanges for a short-lived publish token, scoped to one package and one
pipeline run.

To publish from GitHub Actions with trusted publishing:

1. Configure the package for trusted publishing on npmjs.com, pointing at
   the repository and the workflow environment that publishes it.
2. Remove the `NPM_TOKEN` variable from the workflow.
3. Keep `id-token: write` in the workflow permissions; ReelOut and the
   package manager exchange the identity token automatically.

ReelOut verifies trusted publishing before publishing: when OIDC tokens are
available it exchanges the identity token for each package targeting the
public npm registry. npm and pnpm prefer OIDC even alongside an `NPM_TOKEN`;
a rejected exchange warns and falls back to the `NPM_TOKEN` or ambient
registry credentials when they exist, and fails the release when they do
not. Yarn Berry publishes with OIDC alone: a rejected exchange always fails
the release, while configured registry credentials skip the OIDC path
entirely and publish with the token instead. The publish itself relies on
the package manager's native OIDC support, so ReelOut fails fast when the
installed CLI predates it: npm 11.5.1 or later, pnpm 11.0.0 or later, or
Yarn Berry 4.3.0 or later.

Yarn Berry publishes through OIDC on GitHub Actions, GitLab CI, and
CircleCI:

- GitHub Actions needs `id-token: write`; GitLab CI and CircleCI need a
  pre-issued `NPM_ID_TOKEN` instead.
- CircleCI support requires Yarn 4.4.2 or later.
- Yarn Berry only attempts OIDC when no registry credentials are
  configured in `.yarnrc.yml`; a configured token publishes with that token
  instead.
- When `NPM_TOKEN` publishes instead, ReelOut injects it as
  `YARN_NPM_AUTH_TOKEN`, which Yarn Berry applies only to its default
  registry; other publish registries keep their `.yarnrc.yml` credentials
  and the injection is skipped with a warning.
- Yarn Berry exchanges against the public npm registry or its
  `registry.yarnpkg.com` alias; npm and pnpm only against the public npm
  registry itself.

`.npmrc` files can reference environment variables, for example
`//registry.npmjs.org/:_authToken=${NPM_TOKEN}`. npm expands those
references itself: an undefined variable falls back to the literal
`${NPM_TOKEN}` string — npm's own behavior, which can masquerade as a
credential — so define every referenced variable in the workflow
environment.

## Cargo trusted publishing

Publish to crates.io without storing a `CARGO_REGISTRY_TOKEN`. With crates.io
trusted publishing, the CI platform issues an OIDC identity token that
crates.io exchanges for a short-lived publish token, scoped to one workflow
run.

To publish from GitHub Actions with trusted publishing:

1. Configure each crate for trusted publishing on crates.io, pointing at the
   repository and the workflow environment that publishes it. A crate must
   already exist to be configured, so the first version of a new crate still
   needs an API token.
2. Remove the `CARGO_REGISTRY_TOKEN` variable from the workflow.
3. Keep `id-token: write` in the workflow permissions; ReelOut exchanges the
   identity token automatically.

ReelOut verifies trusted publishing before publishing: when no registry
token is configured and OIDC tokens are available, it exchanges the identity
token for a short-lived crates.io publish token and injects it into
`cargo publish`, failing before publishing when the registry rejects the
exchange. The publish-access pre-flight is skipped on this path, because the
exchanged token carries no user identity. Outside GitHub Actions, set
`CARGO_ID_TOKEN` to a pre-issued identity token to use the same flow.

## CircleCI

Create `.circleci/config.yml`:

```yaml
version: 2.1
orbs:
  node: circleci/node@7

jobs:
  release:
    macos:
      xcode: '26.6'
    resource_class: m4pro.medium
    steps:
      - checkout
      - node/install:
          node-version: '24'
      - run: corepack enable
      - node/install-packages:
          pkg-manager: pnpm
      - run: npx reelout

workflows:
  release:
    jobs:
      - release:
          context: reelout
          filters:
            branches:
              only: main
```

Set `NPM_TOKEN` and the appropriate hosting token (`GITHUB_TOKEN` or
`GITLAB_TOKEN`) in a shared context or as project environment variables. A
Linux machine executor can be used instead of the macOS executor.

## Shallow checkouts

ReelOut detects shallow repositories and fetches missing history and tags as
needed, so the default `actions/checkout` configuration usually works without
a `fetch-depth` override. If your CI environment restricts `git fetch`, use a
full checkout with `fetch-depth: 0`.

## Debugging in CI

In GitHub Actions, ReelOut enables verbose logging when `RUNNER_DEBUG` or
`ACTIONS_STEP_DEBUG` is truthy. In other CI environments, pass `--debug` to
enable it.

Publish commands (`npm publish`, `cargo publish`, and friends) keep their
output out of the job log by default: a successful publish prints nothing,
and a failed one surfaces the command output through its error message.
Re-run the job with `--debug` to stream the package manager output into the
job log live. See [Troubleshooting](./06-troubleshooting.md).
